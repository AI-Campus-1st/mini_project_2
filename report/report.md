# 서울시 카페 출점 후보 선정 대시보드

## 1. 대시보드가 답하는 질문

### 청중과 의사결정

이 대시보드는 **서울에서 카페 출점을 검토하는 창업자 또는 출점 담당자가 현장 조사에 우선 투입할 자치구를 선택하도록 돕는 것**을 목표로 한다. 질문은 "생활인구 규모, 기존 카페 수, 최근 변화, 거주인구 대비 활동 수준을 함께 고려할 때 어느 자치구를 먼저 검토할 것인가?"이다.

기존 대시보드에 제시된 결론은 **송파구를 우선 검토하고, 노원구와 서초구를 후속 후보로 비교한다**는 것이다. 다만 점수 3위가 구로구로 바뀌어 기존 후속 후보 순서는 재검토해야 한다. 이는 특정 점포의 계약이나 예상 매출을 확정하는 판단이 아니라, 자치구 수준의 1차 후보 선정이다.

거주인구만으로는 출퇴근이나 외부 활동으로 지역에 머무는 인구를 충분히 설명하기 어렵다. 따라서 주민등록 인구·카페 현황에 시간대별 생활인구를 결합했다. 이 프로젝트에서 생활인구는 특정 시각에 지역에 존재하는 인구를 뜻하며 거주자를 포함한다. 통행량, 순방문자 수, 카페 고객 수와 동일한 개념으로 해석하지 않는다.

| 생활인구 | 서울 Open API `Spop250mLocalResdJachi` | 2026-01-01~2026-06-30, 서울 25개 자치구, 수집 08~23시·분석 08~22시 | 시계열·평일/주말·활동 수준 분석 |

### 수집·정제·적재 과정

수집기는 `python -m collector`로 실행한다. `config.py`에서 기간·지역·시간대를 정하고, `sources/flow_pop.py`에서 날짜를 `YYYYMMDD`로 변환해 요청 URL을 구성한다. `httpx.AsyncClient` 하나를 공유하고 `asyncio.gather`로 데이터를 수집한다.. `Semaphore(5)`로 동시에 수행하는 요청을 5개로 제한하며, 요청 타임아웃은 30초이다.

응답 행은 원본 CSV로 저장한 뒤 `transform.py`에서 날짜·시간·지역 코드·전체 생활인구와 성별 합계 컬럼으로 정리한다. 카페는 업종명으로 필터링하고, 거주인구는 서울시 행을 자치구별로 합산한다. 정제 데이터는 `loader.py`를 통해 DB에 적재한다. 보관 범위는 08~23시로 유지하되, `db/__main__.py`의 원본 조회와 세 생활인구 마트 함수에서 08~22시(양 끝 포함)만 선택한다. 대시보드의 시간대별 마트 조회에도 같은 필터를 적용했다. 월평균·증가율·활동 배율·조건·우선순위는 이 필터를 거친 생활인구에서 계산한다.

개발 중에는 비동기 함수의 호출에 `await`를 연결하고 진입점을 `asyncio.run(main())`으로 변경했다. 날짜 객체가 URL에 시간까지 포함해 들어가던 문제는 `strftime("%Y%m%d")`로 해결했다. pandas의 DB 연결 경고에는 조회용 SQLAlchemy 엔진을 추가하는 방식으로 대응했다.

### 현재 구현의 범위

현재 API 실패는 로그를 남기고 빈 결과를 반환한다. 재시도·백오프, 초당 요청 수 제어, 실패 작업만 이어받는 체크포인트는 구현되어 있지 않다. 동시 요청 5개 제한은 초당 요청량 제한과 다르다. 요청 범위는 `/1/365/`로 고정되어 있어 응답 총건수 기반 페이지 순회도 추가 확인이 필요하다.

DB 적재에는 UPSERT를 사용하지만, 수집기를 다시 실행하면 설정된 전체 기간을 다시 요청한다. 따라서 “실패 지점부터 이어서 수집한다”는 기능을 완료했다고 기술하지 않는다. 원본 CSV도 고정 경로에 저장되어 이전 실행 파일을 덮어쓰므로 수집일별 보관이 필요하다.

## 3. 아키텍처와 DB 설계

```mermaid
flowchart LR
    A[생활인구 API와 카페·거주인구 CSV] --> B[collector: 수집·정제·적재]
    B --> C[(MariaDB: 정제 테이블)]
    C --> D[db: Pandas 마트 집계]
    D --> E[(MariaDB: 마트 테이블)]
    E --> F[app: SELECT·캐싱·시각화]
```

### 계층 분리 의도와 실제 구현

| 계층 | 주요 파일 | 책임 |
| --- | --- | --- |
| 수집 | `collector/__main__.py`, `sources/`, `transform.py`, `loader.py` | 외부 데이터 요청, 정제, DB 적재 |
| 저장·집계 | `db/schema.sql`, `db/build_mart.py`, `db/__main__.py` | 스키마 정의와 마트 생성 |
| 화면 | `app/main.py`, `app/views/repository.py`, `app/charts.py`, `app/components.py` | DB 조회, KPI, 차트, 결론 전달 |

대시보드는 수집기를 호출하지 않고 마트 테이블을 조회한다. API 수집 시간과 화면 조회를 분리하고, 화면에서 대용량 원본을 매번 집계하지 않도록 설계했다. 조회 함수에는 `st.cache_data(ttl=3600)`을 적용했다. 캐싱에 따른 속도 개선 수치는 아직 측정하지 않았다.

현재 `db/__main__.py`는 수집 계층의 연결·적재·로깅 함수를 가져온다. 수집기와 화면 간 직접 의존은 없지만, DB 계층과 수집 계층의 공통 기능 분리는 추가 개선 대상이다. 화면 쿼리는 SELECT 전용이나 DB 계정 권한까지 읽기 전용으로 제한했는지는 별도 검증이 필요하다.

### 테이블 구성과 계약

| 테이블 | 한 행의 기준 | 역할 |
| --- | --- | --- |
| `de_facto_population_raw` | 자치구 × 날짜 × 시간대 | 최소 정제한 생활인구 |
| `cafe_clean` | 카페 코드 | 카페 현황 |
| `population_clean` | 자치구 이름 | 거주인구 |
| `state_dim` | 자치구 코드 | 코드·이름 매핑 |
| `mart_monthly_de_facto_population_per_time` | 월 × 시간대 | 전체 시간대 추이 |
| `mart_state_monthly` | 자치구 × 월 | 월평균·평일/주말·카페 지표 |
| `mart_state_hourly` | 자치구 × 월 × 일 유형 × 시간대 | 시간대 상세 분석 |
| `mart_priority_score` | 자치구 코드 | 출점 비교 점수·조건 |

기본키로 각 테이블의 입도를 고정하고 날짜·지역·시간대 조회용 인덱스를 선언했다. 상세 컬럼과 타입은 [DB 스키마 문서](../db/README.md)에 정리했다. 외래키는 선언되어 있지 않다. 조인에서는 `many_to_one`, `one_to_one` 검증을 사용하며, 로컬 재계산 결과 월간 마트는 25개 자치구 × 6개월인 150행이었다.

현재 마트 집계는 SQL 집계문이 아닌 Pandas로 구현했다. 가이드라인에서 요구하는 마트 생성 SQL 제출 항목은 별도 보완이 필요하다. SQL은 스키마 정의, 조회, UPSERT에 활용했다.

가이드라인의 분리 검증 요구를 확인하기 위해 아래 테스트를 제안한다. 이 표는 실행 완료를 의미하지 않는다.

## 4. 대시보드 구성과 지표 정의

### 화면 흐름

첫 화면에서 “송파구, 노원구, 서초구 순으로 카페 출점 후보 선정”이라는 결론을 보여주고, 조건 충족 자치구 수·전체 자치구 수·충족 지역을 KPI로 제시한다. 이후 우선순위 점수와 개별 지표를 비교하고, 월별 시간대 생활인구와 주말 집중도로 운영 전략을 탐색한다.

SCQA 관점에서 상황은 거주인구·카페 수만으로 판단하기 어렵다는 점, 문제는 규모·증가·활동 수준이 지역마다 다르다는 점, 질문은 어떤 지역을 먼저 검토할 것인지, 답은 세 조건을 함께 만족한 후보를 우선 검토한다는 것이다. 실제 UI는 탭이 아닌 사이드바 페이지 이동 방식이다.

| 차트·영역 | 표현 방식 | 선택 이유 |
| --- | --- | --- |
| 조건 충족 현황 | KPI와 표 | 후보 수와 판단 기준을 먼저 전달 |
| 월별 시간대 생활인구 | 월별 선그래프 | 시간대 패턴과 월간 차이를 비교 |
| 카페당 생활인구·활동 배율 | 자치구별 가로 막대 | 긴 지역명과 지역 간 크기 비교에 적합 |
| 증가율 | 양수·음수 막대 | 증가·감소 방향을 구분 |
| 우선순위 점수 | 순위형 가로 막대 | 비교 후보의 순서를 확인 |
| 주말 집중도 | 선택 월의 지역별 막대 | 월에 따른 평일·주말 차이를 확인 |

월 선택 필터는 주말 집중도 페이지에 있다. 모든 차트에 공통 적용되는 지역·기간 필터는 현재 구현 범위로 확인되지 않았다.

### 지표 산식

- **월평균 생활인구:** 자치구·날짜별 08~22시의 15개 시간대 평균을 구한 뒤 월별로 일평균을 평균한다.
- **최근 3개월 생활인구:** 2026년 4~6월 월평균의 산술평균이다. 직전 기간은 1~3월이며 월별 일수 가중평균은 아니다.
- **생활인구 활동 배율:** 최근 3개월 평균 생활인구 ÷ 2026년 6월 거주인구.
- **카페 1개당 생활인구:** 최근 3개월 평균 생활인구 ÷ 2026년 6월 카페 수.
- **최근 생활인구 증가율:** `(최근 3개월 평균 / 직전 3개월 평균 - 1) × 100`.
- **주말 집중도:** 선택 월의 주말 평균 생활인구 ÷ 평일 평균 생활인구. 토·일을 주말로 구분한다.
- **우선순위 점수:** `100 × (0.5 × P(카페당 생활인구) + 0.3 × P(증가율) + 0.2 × P(활동 배율))`. `P(x)=(오름차순 최소 순위-1)/(자치구 수-1)`이며 동점에는 최소 순위를 부여한다.

점수는 원래 단위가 다른 세 값을 그대로 더하지 않고 상대 순위로 변환한 뒤 가중합한다. 50:30:20 가중치는 프로젝트의 판단 기준이며 매출 예측으로 검증된 계수가 아니다.

조건 점수는 ① 카페당 생활인구가 자치구별 지표의 산술평균 초과, ② 증가율이 0% 초과, ③ 활동 배율이 1배 초과일 때 각각 1점이다. 총 0~3점으로, 100점 척도의 우선순위 점수와 별개이다.

## 5. 핵심 인사이트 초안

이 절은 기존 `app/components.py`와 홈 화면에 작성된 후보 선정 판단을 정리한 것이다. 새로운 분석 방향을 추가하지 않았으며, 최종 해석은 작성자가 검토한다.

### 기존 결론을 뒷받침하는 수치

정제 CSV에 08~22시 필터를 적용한 마트 함수를 실행해 재계산한 결과는 다음과 같다. DB의 `BIGINT` 적재 과정에서 소수점이 달라질 수 있어 운영 DB 결과와는 소폭 차이가 있을 수 있다. 전체 재계산 값은 [검증용 CSV](priority_score_verification.csv)에 저장했다.

| 지역 | 점수 순위 | 우선순위 점수 | 증가율 | 활동 배율 | 카페당 생활인구 | 충족 조건 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 노원구 | 1 | 69.17점 | -0.85% | 1.07배 | 754.53명/개 | 2개 |
| 송파구 | 2 | 67.50점 | +0.43% | 1.19배 | 573.76명/개 | 3개 |
| 구로구 | 3 | 65.00점 | -0.72% | 1.07배 | 648.11명/개 | 2개 |
| 서초구 | 4 | 62.50점 | +1.60% | 1.57배 | 505.28명/개 | 2개 |

카페당 생활인구 조건의 기준인 자치구별 산술평균은 537.05명/개였다. 이는 서울 전체 생활인구를 전체 카페 수로 나눈 값과는 다르다. 25개 자치구 중 세 조건을 모두 충족한 지역은 송파구 한 곳이었다. 기존 화면은 이 조건 충족 여부를 우선해 송파구를 최종 후보로 선택했다. 노원구는 우선순위 점수가 가장 높지만 증가율 조건을 충족하지 않는다. 서초구는 증가율과 활동 배율 조건을 충족하지만 카페당 생활인구 조건을 충족하지 않는다.

따라서 “점수 1위이므로 최종 후보 1위”와 “모든 조건을 통과한 지역을 먼저 검토”는 서로 다른 선택 규칙이다. 기존 결과를 설명할 때는 **조건 충족을 우선하고 점수는 후속 비교에 사용했다**는 판단 순서를 명시해야 한다. 카페당 생활인구가 높다는 사실만으로 공급 부족이나 높은 매출이 입증되는 것은 아니다.

### 분석 시간 변경에 따른 결과 변화

23시를 제외한 뒤 노원구 점수는 70.83점에서 69.17점으로 바뀌었으나 1위를 유지했다. 송파구는 67.50점과 3개 조건 충족을 유지했다. 구로구는 65.00점으로 3위이며 증가율은 -0.72%로 증가 조건을 충족하지 않는다. 서초구는 62.50점으로 4위다. 따라서 기존의 “송파구·노원구·서초구” 고정 문구를 새로운 점수 상위 3개 지역으로 설명해서는 안 된다. 후속 후보에서 성장 조건을 우선할지 종합 점수를 우선할지 작성자의 선택 근거가 필요하다.

### 작성자가 완성할 해석

- `[작성자 보완]` 분석 전에 어떤 자치구를 예상했으며, 실제 결과가 어떻게 달랐는가?
- `[작성자 보완]` 점수 1위 노원구보다 세 조건 충족 지역인 송파구를 우선한 이유는 무엇인가?
- `[작성자 보완]` +0.43%라는 작은 증가가 후보 선정에서 얼마나 중요한지, 변동성·계절성까지 고려하면 판단이 달라지는가?
- `[작성자 보완]` 새 점수 3위 구로구와 기존 후보 서초구 중 어떤 기준으로 후속 후보를 선정할 것인가?
- `[작성자 보완]` 후보 자치구 안에서 어떤 역세권·상권을 현장 조사할 것인가?

## 6. 한계와 다음 단계

### 데이터와 해석의 한계

1. **자치구 단위 분석:** 역세권·골목·점포 입지 차이를 설명하지 못한다. 임대료, 실제 매출, 보행 동선, 카페 면적·브랜드도 반영하지 않았다.
2. **시점 차이:** 생활인구는 6개월 시계열이지만 카페와 거주인구는 6월 스냅샷이다. 월별 점포 개폐업과 거주인구 변화는 반영하지 않았다.
3. **계절성:** 1~3월과 4~6월의 차이에 계절·학기·휴일 효과가 포함될 수 있다. 증가율을 출점의 인과적 효과나 장기 성장으로 단정하지 않는다.
4. **추계값과 타입:** 생활인구 CSV는 소수점이 있으나 DB 원본 컬럼은 `BIGINT`이다. 소수점 보존 정책을 정하고 CSV·DB·마트 수치를 대조해야 한다.
5. **결측 처리:** 정제 CSV에 결측이 없다는 사실은 원천 결측이 없었다는 뜻이 아니다. 성별 합계 계산은 `to_numeric(errors='coerce')` 후 `sum()`을 사용하므로 전체 결측 구간도 0으로 바뀔 수 있다. 마스킹 값의 처리 근거와 원본 검증을 보완해야 한다.
6. **스냅샷 구조:** 우선순위 마트에 기준월이 없어 기간별 점수 이력을 별도 보관할 수 없다.

### 제출 전에 우선 정리할 구현·설명 차이

| 항목 | 현재 확인 내용 | 다음 조치 |
| --- | --- | --- |
| 영업시간 | 원본 조회·마트 함수·시간대 마트 조회에 08~22시 필터 적용 완료 | 운영 DB에서 `python -m db`로 재집계 후 Streamlit 캐시 삭제 또는 재시작 필요 |
| 활동 배율 조건 | 홈 문구는 평균 초과, 코드는 1배 초과 | 판단 기준과 화면 문구 통일 |
| 점수 설명 | 화면 캡션에 상대 순위 변환이 생략됨 | 원지표의 단순 가중합으로 오해하지 않도록 산식 보완 |
| 후보 문구 | 송파구 등 결과가 화면에 고정 문자열로 들어 있음 | 데이터 갱신 시 결론 불일치 방지 |
| 빈 결과 | 모든 조건 충족 지역의 첫 행을 직접 참조 | 충족 지역이 없을 때 안내 처리 |
| API 수집 | 재시도·초당 속도 제어·재개 없음 | 실패 작업 기록과 재시도, 요청량 제어 추가 |
| 마트 생성 | Pandas 구현, 집계 SQL 파일 없음 | 가이드라인 제출 요건에 맞는 SQL 보완 |
| 실행 안내 | README에 `python -m build_mart.py` 표기 | 실제 진입점 `python -m db`로 실행 안내 수정 |

08~22시 필터 코드는 앞선 수정에서 적용했고, 08·22시 포함 및 07·23시 제외와 월평균 계산을 검증했다. 이번 리포트 갱신에서는 로컬 CSV 재계산 결과를 반영했다. 운영 DB의 마트 재집계와 앱 실행 검증은 수행하지 않았다. 표의 나머지 항목은 제출 전 보완 사항이다.

## 7. 선택 확장과 검증 계획

SQLAlchemy 조회와 1시간 캐싱, 별도 `transfer_data.py`를 이용한 DB 이전 코드를 준비했다. 다만 캐싱 전후 응답시간, 실제 서버 이전 성공, 배포 URL은 이번 검토에서 확인하지 않았으므로 심화 성과로 확정하지 않는다.

다음 검증에서는 앱 초기 로딩과 캐시 적중 조회 시간을 각각 측정하고, 더미 데이터 및 빈 결과에서 화면이 동작하는지 확인한다. API 단절 상태에서 기존 DB만으로 화면이 유지되는지, 화면용 계정이 SELECT만 허용하는지도 검증한다. 최종 제출 시 실행 환경·일시·결과와 화면 캡처를 함께 기록한다.

## 8. AI 활용 기록

| 활용 영역 | 지원 내용 | 작성자 검토 사항 |
| --- | --- | --- |
| API 구현 보조 | asyncio·HTTPX 호출 구조, 날짜 포맷 문제 설명 | 동시성과 요청량 제한의 차이, 실패 처리 설명 |
| DB 구현 보조 | import 오류, SQLAlchemy 연결, 이전 코드 안내 | 연결·트랜잭션·스키마 보존 범위 이해 |
| 시각화 구현 보조 | Plotly 차트와 조건 점수 함수 예시 | 지표 산식과 차트 해석, 코드 동작 설명 |
| 문서화 | requirements와 스키마 문서 작성, 리포트 구조화 | 실제 구현·결과와 일치 여부 검토 |
| 검증 보조 | 로컬 CSV 건수·중복·결측 확인, 기존 함수로 점수 재계산 | 운영 DB 결과와 대조 및 최종 판단 |

분석 주제와 후보 선정 문장은 기존 프로젝트에 작성된 내용을 바탕으로 했다. AI가 제안한 코드를 활용한 사실을 기록하며, 분석 결과의 최종 해석과 선택 기준은 작성자가 자신의 언어로 설명한다. 예상과 달랐던 점과 개인적인 학습 경험은 임의로 만들지 않고 보완 항목으로 남겼다.
